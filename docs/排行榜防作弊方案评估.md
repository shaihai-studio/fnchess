# 排行榜防作弊方案评估（计划稿）

> 用途：娱乐 + 半正式比赛场景下的排行榜防作弊加固，供团队评估选型。
> 日期：2026-08-05
> 现状：纯前端游戏，身份（playerId）+ 成绩（LR∑/分关竞速用时）均由客户端生成并上报，服务器只做"信任收下 + 弱风控"。

---

## 0. 当前作弊面（为什么需要加固）

排行榜"判断这是谁、分是多少"完全依赖客户端：

- **身份** = 浏览器 `localStorage` 里的随机 UUID（`playerId`），前端自生成、自上报。
- **成绩** = 前端结算算好 `value` 后发给服务器，服务器不验证来源。

服务器目前仅有的防护：

| 防护 | 机制 | 局限 |
|---|---|---|
| IP 风控 | 同 IP 60 分钟内最多 5 个"新身份" | 只拦零成本无限小号；反复刷已有 playerId 不触发 |
| 数值上限 | LR∑ ≤ 1e9、用时 1s~1e6s | 只拦明显脏数据 |
| 只记最高 | `value ≤ cur.score` 忽略 | 避免恶意覆盖/降级 |

**可被钻空子的点：**

1. **身份/分数自说自话（最致命）**：F12 控制台直接伪造任意 `playerId` + 任意高 `value` 上报，服务器无法验证该分是否真由合法对局产生。
2. **绕过 IP 风控**：反复用小号刷同一个 playerId 的分数（不产生新身份），风控不触发。
3. **伪造本地成绩**：改 localStorage 里的"每关最佳表达式长度/最佳用时"，让前端算出假分再上报。

**结论：当前实现可作弊且门槛极低，但作为纯娱乐定位已"够用"。半正式比赛需要加固。**

---

## 1. 排行榜分数本质（决定方案设计）

排行榜分数**不是单局分数**，而是跨所有关卡"最佳成绩"的汇总：

- **LR∑**（闯关榜）= Σ 每关 `100 / (10 + 该关最短表达式长度)`，最短长度存在 `localStorage`。
- **分关竞速榜**（`rt{N}`）= 每关最短通关用时（秒），服务器取更短，存在 `localStorage`。

判定链（谁能算出"通关"）：

```
玩家输入表达式 → FunctionParser.evaluate(expression, x) 求值
  → 高精度采样成折线（sampleFunction）
  → CollisionDetector 用 Canvas 坐标 + 像素容差做视觉相交检测
  → hitTarget && !hitForbidden = 通关
```

⚠️ **关键难点**：命中判定依赖 `GridSystem.mathToCanvas`（画布坐标换算）和**像素容差**，不是简单的"在目标格 x 处求 y 是否等于目标 y"。这意味着"服务器完整复算"必须把这段坐标换算抽象成**与 Canvas 解耦的纯数学函数**，否则前后端不一致会误判。

## 2. 三档方案

### 方案 A：HMAC 签名校验（推荐先做）

**改动量**：★★ 小　|　**防作弊力**：★★★★　|　**成本**：低、见效快

**核心思想**：不让客户端裸传 `value`，服务器下发一次性 `nonce`，客户端用共享密钥对提交内容做 HMAC-SHA256 签名，服务器验签 + 查 nonce 有效性后才入库。

**服务器侧（server/index.js）**
- 连接时生成每连接唯一 `nonce`（可带有效期），下发 `challenge` 消息。
- `handleSubmitScore` 增加验签：Node 内置 `crypto.createHmac('sha256', SECRET)` 重算签名比对；校验 nonce 未被复用 / 未过期。

**客户端侧（LeaderboardService.js）**
- 维护服务器下发的 `nonce`。
- 提交前用浏览器 `crypto.subtle`（HMAC-SHA256，异步）对 `(playerId, boardType, value, nonce, 关卡最佳数据)` 签名。

**技术底座已具备**：
- 服务器有 Node 内置 `crypto`。
- 前端有 Web Crypto `crypto.subtle`。
- 项目已有 `SeedCrypto.js`（XOR + FNV 签名 + 盐）可作备选/兜底。

**防住**：直接改 `submit_score` 的 value / 伪造 playerId 刷分——无 valid nonce + 密钥签名，服务器直接丢弃。
**防不住**：硬核玩家逐关打出真成绩后用合法流程上报（签名只证明"我提交了这个值"，不证明"值来自合法对局"）。
**评估**：半正式场景下已大幅抬高门槛，不再是"改个数字就上榜"。

**信任模型前提**：SECRET 为硬编码共享密钥，依赖"前端源码不易被改"兜底。**若部署在别人能看源码的公共环境，密钥会泄露，需升级为方案 B/C 或服务端签发会话**。

---

### 方案 B：服务端复核关键高分

**改动量**：★★★★ 大　|　**防作弊力**：★★★★☆　|　**成本**：高（逻辑移植）

**核心思想**：在方案 A 基础上，对**进入前列（如 TOP 5）的高分**做抽查复核——服务器向客户端"索要"该高分对应的每关表达式，用与前端一致的算法在 Node 端复算，验证"该表达式确实能以 N 步通关该关 / 该用时确实对应某关"。

**需要移植/抽象到 Node 的部分：**
- `FunctionParser.evaluate`（纯数学，易移植）。
- 命中判定：将 `GridSystem.mathToCanvas` + `CollisionDetector` 的"采样折线 + 像素容差相交检测"**抽成与 Canvas 解耦的纯函数**（当前依赖 `gridSystem` 实例，需抽公共模块）。
- 官方关卡数据内置一份（`campaignLevels.js`）。
- 竞速关是**随机种子生成**的，需把**种子**也上报，服务器用 `createSeededRandom` 重建关卡。

**防住**：伪造"该关最短长度 N / 该关用时 T"但拿不出真能通关的表达式，服务器判定失败。
**难点**：命中判定含"像素容差 + 采样密度"，与画布尺寸/范围耦合，必须和前端**完全一致**才不会误判——这是移植工作量最大的地方。**只复核上榜高分段**可大幅控制成本（不必每关全复算）。

---

### 方案 C：全流程服务端权威

**改动量**：★★★★★ 重构级　|　**防作弊力**：★★★★★　|　**成本**：极高

**核心思想**：从对局开局起，逐步上报"每步输入 + 关卡数据"，服务器按帧复算整局，算出的成绩才是权威。等于把游戏核心逻辑在服务器完整实现一遍。

**防住**：一切客户端伪造（因为权威结果只由服务器产生）。
**评估**：适合正式竞技平台；对当前纯前端架构是重构级，不建议现在做。

## 3. 方案对比一览

| 维度 | A. HMAC 签名 | B. 服务端复核高分 | C. 全流程权威 |
|---|---|---|---|
| 改动量 | ★★ 小 | ★★★★ 大 | ★★★★★ 重构级 |
| 防作弊力 | ★★★★ | ★★★★☆ | ★★★★★ |
| 防"改数字刷榜" | ✅ | ✅ | ✅ |
| 防"逐关刷真成绩" | ❌ | ✅ | ✅ |
| 防"伪造本地最佳" | ⚠️（签名合法即通过） | ✅ | ✅ |
| 服务器是否跑游戏逻辑 | 否 | 部分（复核时） | 是 |
| 落地周期 | 短 | 中~长 | 长 |
| 推荐阶段 | 第一步 | 上榜后叠加 | 暂不做 |

---

## 4. 建议落地路径

1. **立即做方案 A**：HMAC 签名 + nonce，堵住"改数字刷榜"，成本低、见效快（Node `crypto` 与前端 `crypto.subtle` 均已具备）。
2. **上榜后叠加方案 B**：只复核前列高分段，避免全量复算的高移植成本，针对性防"逐关刷真成绩"。
3. **方案 C 暂缓**：等确实出现规模化作弊且业务升级为正式排名时再考虑。

---

## 5. 选型前需团队确认的开放问题

1. **服务器信任模型**：服务器是我们自建、只有我们能改的吗？（决定方案 A 的硬编码 SECRET 是否够用；公共环境需升级会话签发。）
2. **范围**：本次先只做方案 A，还是直接上方案 B？
3. **覆盖维度**：竞速分关榜（`rt{N}`）、闯关 LR∑ 都纳入防护吗？还是先护闯关 LR∑？
4. **复核阈值**：方案 B 若做，"上榜高分段"的门槛定多少（TOP 5 / TOP 10）？
5. **提交频率/nonce 策略**：nonce 是一次一用还是带短时效可复用？影响实现复杂度与重放风险。
