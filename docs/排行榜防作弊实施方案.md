## 1. 总体架构（双通道）

提交时按"该次成绩是否需要权威核验"分流：

```
submit_score(boardType, value, payload, sig)
        │
        ├─ 签名校验（方案 A，必经）
        │     sig 无效 / nonce 复用 / nonce 过期  → 直接丢弃（不入库）
        │
        ├─ 是否触发核验通道？（方案 B，仅 LR∑ 榜，依据 D1 阈值判定）
        │     │
        │     ├─ 否（普通分 / 冷启动）→ 签名通道：直接按签名内容入库
        │     │
        │     └─ 是（高分 / 超下一名 50）→ 核验通道：
        │           服务器逐关复算 → 整批拒绝 + 细化报错（依据 D3）
        │
        └─ 闸门（D2）：签名通道 20~30s / 核验通道 2min 起 + 指数退避
```

- 竞速分关榜 `rt{N}`：始终走签名通道（D5），不经核验分支。
- 闯关 LR∑ 榜：按 D1 阈值在签名/核验间分流。

## 2. 早期榜单阈值 / 冷启动策略（D1）

核心问题：冷启动时 `lrCommunityMax` 很低，`T = lrCommunityMax − 100` 会为负或极小正数，导致**几乎所有提交都触发核验** → 卡服且误伤。

### 2.1 三档递进

```
N = lr 榜去重玩家数
M = lrCommunityMax（当前最高分）

档位判定：
  1) N < 10（冷启动）     → 关闭方案二，全员走签名通道。
                           理由：无作弊空间也无信誉损失，不值得用核验拖慢。
  2) 10 ≤ N < 50（成长期） → 方案二只对"接近榜首"的极少数启用：
                             T = max( M − 100,  ceil(M × 0.8) )
                             仅当 该玩家本次有效分 ≥ T 才触发核验。
                             （乘以 0.8 兜底：防止分数极度集中时 M−100 误伤）
  3) N ≥ 50（成熟期）      → 原方案：T = M − 100。
```

### 2.2 强制核验：超下一名 50 分

防止"跳档型"作弊——即便没到阈值附近，只要该玩家新分数**超过其下一名 50 分以上**，也应强制核验：

```
下一名分 = 榜上最高且 < 该玩家新分 的那个分数（即被挤下去的那位）
if (该玩家有效分 − 下一名分) > 50  → 强制走核验通道
```

> 说明：`N`、`M`、下一名分均由服务端从 `scoreBoards.lr` 实时读取，客户端传来的分数只用于"判断是否触发"，**不以客户端分数作为入库值**。

## 3. 提交闸门与限速（D2）

### 3.1 分级闸门

| 通道 | 建议最小间隔 | 依据 |
|---|---|---|
| 签名通道（方案一，普通分） | **20~30 秒** | 验签服务器零成本，纯防刷请求风暴 |
| 核验通道（方案二，高分） | **2 分钟** | 复算有成本，但冲榜玩家可接受 |

> 5 分钟对"刚打通一关想立刻刷高一点"的玩家劝退；核验单次复算实测极低（每关采样数百点、毫秒级，90 关合计百毫秒级）。真正要防的是"脚本无限刷"而非"单次贵"。

### 3.2 高频核验指数退避

签名通道只做固定间隔；核验通道对**同一 playerId/IP** 做自适应退避：

```
记录 lastVerifyAt[playerId] 与 recentVerifyCount（5 分钟滑动窗口）

submit → 核验通道：
  if (now − lastVerifyAt) < currentGate  → 拒绝（429：太频繁）
  currentGate 初始 = 2min
  连续核验 ≥2 次（5 分钟内）→ gate 指数放大：
     第1次后 = 2min
     第2次后 = 5min
     第3次后 = 15min
     ...
  recentVerifyCount ≥ K（如 5）→ 当日锁定核验（只能走签名通道或拒绝）
```

这样**正常玩家（偶尔刷）等 2 分钟，脚本（高频刷）被指数拖死**，最平衡。

## 4. 方案二核验通道实现（核心）

### 4.1 触发后的数据契约

核验通道下，客户端除签名内容外，还需附上**逐关表达式**（方案 B 的"索要每关表达式"改为"随高分提交一并带来"，减少一轮往返）：

```
payload = {
  boardType: 'lr',
  value: <客户端算出的 LR∑>,            // 仅用于比对，不入库
  levels: [
    { level: 1,  expr: 'y=...', minLenClaimed: 3, cleared: true },
    { level: 2,  expr: 'y=...', minLenClaimed: 4, cleared: true },
    ...
  ]
}
sig = HMAC_SHA256(SECRET, nonce + playerId + boardType + value + JSON(levels))
```

> 普通分（签名通道）**不需要**带 `levels`，降低常规上传体积。

### 4.2 服务器复算流程

与前端一致的数学链（见选型稿 §1）：

```
for each level in payload.levels:
    def = campaignLevels[level]                  // 官方 targetCells/forbiddenCells
    f = FunctionParser.evaluate(expr)            // 纯数学，易移植 Node
    samples = sampleFunction(f, def.range)       // 与前端同密度采样
    ok = hitTarget(samples, def) && !hitForbidden(samples, def)
    if !ok:  记 failed[level] = 'not_pass'
    realMinLen = tokenCount(expr)               // D4：原始表达式词法切分，不做化简
    if realMinLen != minLenClaimed: 记 failed[level] = 'length_mismatch'
recomputedSum = Σ 100 / (10 + realMinLen_i)  for passed levels
if abs(recomputedSum − value) > 1e-6:  记 globalFail = 'value_mismatch'
```

### 4.3 整批拒绝 + 细化报错（D3，重点）

**原则：要么全对、要么全错，整批拒绝。** 不做部分计入。

理由（选型稿未展开，此处定稿）：
1. **部分计入会被利用成免费 oracle**：作弊者可故意在某一关传错、观察服务器是否"部分通过"，从而逐关试探出哪些表达式是可信的 → 探测出最优解。整批拒绝堵死该通道。
2. **语义清晰**：不会出现"分变高了却没涨"的困惑。
3. **诚实玩家不会命中**：整批拒绝只在表达式确实通不过/被篡改时触发，前端正常流程不会产出这种提交（除非前端 bug，属可定位问题）。

**返回结构（细化报错）**：

```
// 失败
HTTP 200 / JSON:
{
  ok: false,
  code: 'verify_failed',
  reason: 'not_pass' | 'expr_mismatch' | 'length_mismatch'
         | 'value_mismatch' | 'too_many_cleared' | 'level_not_open',
  level: 7,                       // 第一个出错的关卡号
  detail: 'level 7: expression did not hit target after re-compute'
}
// 成功（核验通过）→ 用服务器复算的 recomputedSum 入库（不信任客户端 value）
{
  ok: true,
  score: recomputedSum
}
```

**错误码定义（服务端权威，前端中文映射）**：

| reason | 含义 | 诚实玩家是否可能触发 |
|---|---|---|
| `invalid_signature` | 签名失败 / nonce 失效 | 否（方案一就拦） |
| `not_pass` | 该关表达式复算后未命中目标 / 命中禁区 | 否（前端已判定通关才上报） |
| `expr_mismatch` | 表达式与签名原文不一致（被篡改） | 否 |
| `length_mismatch` | 上报最短 token 数与服务器复算 token 数不符 | 否 |
| `value_mismatch` | 复算 LR∑ 与客户端 value 偏差超 1e-6 | 否 |
| `too_many_cleared` | 通关数量异常（如单次声称清了远超实际的关） | 否 |
| `level_not_open` | 上报了未开放关卡的成绩 | 否 |
| `rate_limited` | 闸门/指数退避拒绝（D2） | 偶发（正常玩家 2min 内重提） |

> 设计要点：**失败只报"第一个出错关"**，不一次性抖出所有错误（避免给作弊者逐关 oracle 信号，只暴露边界）。

### 4.4 入库值以服务器为准

核验通过时，**用 `recomputedSum` 入库**，而非客户端 `value`。即使客户端算错（多报），也只记服务器复算的、经核验的真实分。

## 5. 长度口径：token 数（D4，最终口径）

> **最终规则**：token 用**原版计数、不化简**。括号不算；连续数字（含小数点）算一个（如 `123`、`1.23`）；单个常数（`x`/`e`/`π`/`i`）算一个；运算符 `+ - * / ^` 各算一个；函数名算一个。不做任何代数化简（`sin0` 不折成 `0`，`2π` 不归并，`x-x` 不消）。

| 类别 | 计数 | 示例 |
|---|---|---|
| 数字字面量（连续数字含小数点，算 1 个） | 1 | `123`、`1.23`、`0.0001` |
| 单变量 / 常数 `x` `e` `π` `i` | 1 | `x`、`π` |
| 运算符 `+ - * / ^` | 各 1 | `+`、`^` |
| 括号 `( )` | **不算** | — |
| 函数名 `sin/cos/tan/log/exp/...` | 1 | `sin`、`exp` |

示例：`y=sin0+21.5x-x+0.5` → `sin`/数字`0`/`+`/数字`21.5`/`x`/`-`/`x`/`+`/`数字0.5` = 9 token（括号不计入）。
前后端共用同一数组切分逻辑，**不加 simplify / mathjs**，并补一致性单测。

> **已与游戏现有口径对齐（2026-08-05 核实）**：游戏里 LR∑ 与星星本来就用同一套原始 token 计数，且**本就不化简**：
> - `UIInput.getCurrentExpressionLength`（UIInput.js:1061）与 `FunctionParser.analyzeFunctionType`（FunctionParser.js:437 / ExpressionAnalyzer.js:254）用的是**完全相同的 token 正则** `/ (sin|cos|tan|...|factorial) | (\d+(?:\.\d+)?) | (PI|π|e|i) | ([+\-*/^!]) | (x) /gi`，先 `replace(/\s+/g,'').replace(/[()（）]/g,'')` 再去数，无 simplify、括号不计、数字贪婪。
> - LR∑ 用 `100/(10+best)`（best=该 token 数）；星星用 `length` 映射：≤2→5★、3–5→4★、6–9→3★、10–15→2★、≥16→1★。
> - **服务端 `verifyLRSigma` 必须逐字复用 `analyzeFunctionType` 的正则与 `length===0 && cleanExpr.length>0 → length=cleanExpr.length` 兜底，不能自造一套**，否则与客户端 LR/星星不一致。
> - **严禁 simplify/normalize**：锁元素关卡（如某关锁全部数字 0–9+`.`）玩家被迫用更长表达式；normalize（如 `x+x→2x`、`8+1→9`）会把被锁代价抹掉，使锁形同虚设、并破坏 LR/星星公平性。

## 6. 竞速榜不纳入方案二（D5）

### 6.1 原因

- 竞速榜 `rt{N}` 是"用时"榜，不是"表达式分"榜。方案二核心（用表达式复算得分、防伪造分数）对"防竞速作弊"**无效**：玩家可手打慢解、却上报"最优解"假装快，复算表达式无法验证其手速。
- 竞速作弊本质是"改本地计时"，需**重放验证**（服务器回放该关落子序列 + 用时），那是另一套机制，不在方案二范畴。
- 硬套会污染：竞速关表达式不该作为"该关最优解"众包来源，会与 LR∑ 最优解池混淆。

### 6.2 竞速的防线（含难度变量，2026-08-05 修订）

- 仅签名通道（方案 A）+ **20s 限速**。
- 轻量 sanity check（可选，非方案二）：上报附带 `solvedCount` / `totalRounds`，服务器做**含难度变量的**合理性拦截（过快则拒）。

> **修订原因**：原稿"按 `用时/题数` 拦截"既没定阈值、也没有难度变量——而竞速每关难度差异巨大（见下），单一阈值要么放走作弊、要么误杀正常玩家。

**竞速关难度是确定性、按关号固定的**（`GameController.buildRaceLevel` 的 `levelConfigs`，每关 `allowed`/`forbidden`/`fixedLocks`/`randomLocks`/`mustLock` 固定；坐标虽每次随机 seed，但难度参数不变）：

| 关号 | allowed(目标) | forbidden(禁区) | locks | 性质 |
|---|---|---|---|---|
| 1 | 1 | 1 | 0 | 极简 |
| 10 | 2 | 4 | 13+1 | 锁大量元素 |
| 21 | 2 | **200** | 0 | 墙关 |
| 22 | 2 | **300** | 2 | 墙关 |
| 27 | 3 | **200** | 1 | 墙关 |
| 30 | 6 | 6 | 6 | 多目标 |

- 每关固定解 `puzzlesPerLevel = 10` 题（`solvedCount` 到 10 才通关上报），上报的 `solvedCount` 必须 =10 才可信。
- **难度变量（与 allowed/forbidden/locks 直接关联，锚定 Lv1 总时长下限 = 1s）**：服务器内置 `levelConfigs`，按关号难度参数算"总时长下限"：
  ```
  floorPerLevel(level) = 1s × ( 1 + kF×(forbidden−1) + kL×(fixedLocks+randomLocks) + kA×(allowed−1) )
  // 系数初值（可调）：kF=0.02（禁区）、kL=0.10（锁元素）、kA=0.20（额外目标）
  if (elapsed < floorPerLevel) → 拒（too_fast，且给出该关难度提示）
  ```
  三项语义：
  - `kF×(forbidden−1)`：禁区越多，找通路越难（Lv1 的 1 个禁区作基准，不计入）。
  - `kL×(fixedLocks+randomLocks)`：锁元素越多，构造越难。
  - `kA×(allowed−1)`：目标越多，每关要多穿的点越多。
  - **锚点**：Lv1（allowed=1, forbidden=1, locks=0）→ 总时长下限 = **1s**（用户拍板）。
  示例（10 题合计下限）：Lv1=1s、Lv10≈2.7s、Lv21≈5.2s、Lv22≈7.4s、Lv27≈5.5s、Lv30≈2.7s。
- **口径说明（防误杀/防绕过）**：
  - `floor` 是**物理绝对下限**（任何人类不可能更快），不是平均成绩，避免误杀；系数需实测校准。
  - `drawDelay` 是玩家可设置的加分项（0/1000/5000ms/题），`floor` **一律按 drawDelay=0 计**——假设无延迟是最快情形，正常玩家实际用时 ≥ solving+delay，永远不会低于 floor；作弊者也无法用"声称 drawDelay=0"绕过。
  - 坐标随机意味着服务器无法复算单局（无 seed），所以本防线只到"按难度配置的下限"这一层，**不解决"改本地计时"**（那需逐落子重放，另起机制，超范围）。

### 6.3 结论

| 维度 | LR∑（闯关） | rt{N}（竞速分关） |
|---|---|---|
| 通道 | 方案一 + 方案二 双通道 | 仅方案一 |
| 核验复算 | 是 | 否 |
| 入库值来源 | 服务器复算 | 客户端签名内容（带 sanity） |
| 闸门 | 签名 20~30s / 核验 2min+ | 签名 20s |

## 7. 服务端逻辑要点（handleSubmitScore / handleReport，不写代码）

以下按职责描述，落地时按此顺序实现，**不要照搬伪代码**：

- **签名校验（方案 A，所有榜必经）**：用 HMAC 校验 `sig`，并校验 `nonce` 一次性且未过期；失败直接丢弃（不入库）。非 `lr`/`rt{N}` 的榜忽略。
- **闸门（D2）**：`lr` 按"是否触发核验"取 2min 起（高频指数退避），`rt{N}` 固定 20s；未过间隔返回 `rate_limited`。
- **竞速 `rt{N}`（D5）**：仅签名通道，校验用量在 1s~1e6s，可附带 `solvedCount`/`totalRounds` 做轻量 sanity；不做权威复算。
- **LR∑ 分流（D1 / D6）**：
  - 需核验（`needVerify`）→ 走方案二：逐关复算 `verifyLRSigma`（§4.2）。
    - 失败：若玩家在 `flaggedForVerify`（被举报）则 `boardRemove` 清分并解除标记；返回 `verify_failed` + 第一个出错关 + reason。
    - 通过：解除被举报标记，用复算的 `recomputedSum` 入库（不信任客户端 `value`）。
  - 不需核验 → 签名通道直接按签名内容入库。
- **`needVerify` 判定（D1+D6）**：
  - 在 `flaggedForVerify` 中 → 强制核验（D6）。
  - `N<10` → 不核验（冷启动）。
  - `10≤N<50` → `T=max(M-100, ceil(M*0.8))`，`value≥T` 或 `value−下一名>50` 才核验。
  - `N≥50` → `value≥M-100` 或 `value−下一名>50` 才核验。
- **举报 `handleReport`（D6）**：不能举报自己；`lastReportAt[我]` 距上次 <90s → `rate_limited`；目标不在 `lr` 榜 → `target_not_found`；通过则把目标加入 `flaggedForVerify`，使其下次 lr 提交强制核验。
- **`verifyLRSigma`（D3 整批拒绝 + 细化报错）**：遍历 `levels`，对每关取官方 `def` → 复算命中/禁区 → 用 §5 口径数 `tokenCount` 与 `minLenClaimed` 比对 → 累加 `100/(10+realTok)`；任一项不符即整批返回失败（只报第一个出错关 + reason）；全部通过且复算总和与客户端 `value` 偏差 ≤1e-6 才认。

## 8. 客户端逻辑要点（LeaderboardService 改造，不写代码）

- **`submitLRSigma`**：本地用 §5 口径算每关 `minLen` 与 LR∑ 值；触发核验则携带 `levels` 载荷（每关含 `expr` + `minLenClaimed` + 供彗星用的 `minToken`），否则仅签名内容；统一走 HMAC 签名 + `nonce` 上报。
- **彗星 `pl{N}`**：`P_lv` 由服务端从 `minToken` 与 `levelBestToken` 算出，客户端只需随 lr 上报 `minToken`，无需单独请求；UI 加「彗星榜」分关 tab（同竞速分关选择器）。
- **举报 `report`**：签名 + `nonce` 上报目标与原因；本地遵守 90s 间隔提示。
- **结果处理**：收到 `verify_failed` 时按 `reason` 中文映射提示"第 N 关（原因）"，让诚实玩家知道改哪。
- **`nonce`** 由连接时服务器 `challenge` 下发，每次提交后作废、下次重新申请。
- **竞速 `submitRaceTime`** 仅签名 + 20s 限速，不带 `levels`（D5）；按 §6.2 附带 `levelId` + `solvedCount`(=10) + `totalRounds`(=10) 供难度下限拦截。

## 10. 落地顺序建议

1. **P1（方案 A 全榜）**：nonce 下发 + HMAC 验签 + IP 风控保留。先护住"改数字刷榜"。
2. **P2（D1/D2 闸门与阈值）**：三档冷启动 + 分级闸门 + 指数退避。**先于**核验逻辑，因为核验触发依赖阈值。
3. **P3（方案二 LR∑ 核验通道，含 D3）**：`verifyLRSigma` 逐关复算 + 整批拒绝 + 细化报错 + 用服务器值入库。
4. **P4（D4 token 系统）**：`tokenCount`（按 §5 最终口径：不化简、括号不计、数字/常数各 1）移植 Node + 前后端一致性单测。
5. **P5（D5 竞速轻量 sanity）**：可选，竞速仅签名 + 20s 限速，先不做权威复算。
6. **P6（D6 玩家举报）**：`handleReport` + `flaggedForVerify` + 90s 间隔 + 被举报者下次 lr 提交强制核验。
7. **P7（D7 彗星机制 + 彗星分关榜）**：`levelBestToken` 维护 + 单关接近度分 + `pl{N}` 分关榜 + 胜利弹窗双展示（规则已定，§14）。

### 11.2 指数退避的两个参数（K 相关，拆开解释）

核验通道对同一 playerId/IP 的退避有两个独立参数，容易混为一谈，拆开定：

**问题一：各级退避间隔（当前 2min → 5min → 15min，指数放大）**
- 含义：第 n 次核验后要等 `gate` 才能再次核验；5 分钟窗口内连续核验 ≥2 次触发指数放大（2min→5min→15min…）。
- 为什么指数而非固定：正常玩家偶尔刷新（首档 2min 可接受）；脚本高频刷会因 gate 越拖越久而逐渐失效，成本随次数指数上升。
- 取值影响：间隔越小→正常玩家更顺、但脚本单窗口内可钻更多次；越大→反之。**建议维持 2/5/15min**：2min 对正常冲榜足够宽松，15min 已是第 3 次"惩罚档"。若仍嫌严可放宽到 3/8/20min，但起步不建议 <2min（否则脚本 1 小时能核验几十次）。

**问题二：当日锁定阈值 K（当前 K=5）**
- 含义：5 分钟滑动窗口内累计核验次数 ≥ K 时，当日锁定该玩家/IP 的核验通道（之后只能走签名通道，或直接拒核验类提交）。
- K 的权衡：太小（如 2）→ 正常玩家"冲榜冲刺"（一晚反复刷高分）被提前锁死；太大（如 20）→ 脚本单日可钻更多核验名额、威慑下降。
- **K=5 的含义**：5 分钟 5 次 = 平均每 60s 一次核验，远超正常人工频率（人不可能每 60s 打出一关高分并提交核验），**只有脚本会踩到**。**建议维持 K=5**。
- 补充：被锁后仍可走签名通道（低分照常），不影响正常游玩，只限制"频繁改高分"。

## 13. 玩家举报机制（D6）

### 13.1 设计目标

- **不卡服**：举报是写操作，必须限速。设**每举报者 90s（1min30s）间隔**，避免举报本身成为请求洪水。
- **作弊速度不能快过举报速度**：被举报者的 lr 分**强制走方案二核验**——一旦被举报，其下一次 lr 提交必须携带逐关表达式并通过服务器复算，否则清分。因此即便作弊者持续刷分，被举报后下一次提交即被审查，无法"跑赢"举报。

### 13.2 流程

```
handleReport(ws, { target, reason }):
  if target == 自己          → bad_report
  if now < lastReportAt[我] + 90s  → rate_limited
  lastReportAt[我] = now
  if target 不在 lr 榜        → target_not_found
  flaggedForVerify.add(target)   // 强制其下次 lr 提交走方案二

// 被举报者下次提交 lr：
needVerify 因 flaggedForVerify.has(id) 返回 true
  → verifyLRSigma 复算：
      通过  → flaggedForVerify.delete(id)，按服务器值入库
      失败  → boardRemove('lr', id) 清分，flaggedForVerify.delete(id)，记作弊名单（可选）
```

### 13.3 客户端

`LeaderboardService.report(targetPlayerId, reason)`：签名 + nonce（同方案 A 体系），上报到 `report` 消息。被举报者的 lr 提交逻辑无需改动——`needVerify` 在服务端自动拦截，被举报者只是"下次提交时被迫多传 `levels` 并等 2min 闸门"。

> 边界：被举报者若长期不再提交 lr，其分保留至下次活动时才核验（与"下次提交核验"模型一致）。若需更主动，可设举报计数阈值达到 `K` 时直接 `boardRemove`，作为可选增强。

## 14. 彗星机制（D7，原暂名"行星"；与星星共存）

### 14.1 命名与定位

- **名字**：推荐 **「彗星」(Comet)**（候选：收敛 / 星核 / 极光）。理由：彗星越接近太阳越亮——对应"**越接近该关全服最优表达式，分越高**"，且延续星星/行星的天体系命名。
- 定位：独立于「星星」的**相对评级**，两者**共存、互不影响、不互相覆盖**。
- 现有「星星」：每关按**绝对** token 阈值得 1–5 星（≤2→5★、3–5→4★、6–9→3★、10–15→2★、≥16→1★），锁元素关结构性无法满星（如锁全部数字的关）→ **不公平**。
- **彗星的公平性**：按**同关相对**比较（你的 token vs 全服该关最优 token）。锁元素关的最优 token 天然更大，你照样能拿高彗星分 → **天然公平**，正好补上星星的短板。

### 14.2 核心机制（越接近全服最优，分越高）

服务器维护：

```
levelBestToken[lv] = 全服该关最短 token（仅从通过校验/核验的合法上报更新，防污染）
```

客户端随 lr 载荷一并上报每关 `minToken[lv]`（即现有 `function_chess_campaign_best_{lv}` 存的 token 数）。

单关彗星分（**满分 10 颗**，按"你的 token / 全服最优"百分比折算）：

```
P_lv = 10 × (levelBestToken[lv] / minToken[lv])   // 追平最优 = 10 颗；保留 1 位小数
```

示例（用户口径）：最佳答案 5 token、你答 10 token → 10×(5/10) = **5 颗（50%）**；最佳 5、你 5 → 10 颗；最佳 2、你 3 → 10×(2/3) ≈ 6.7 颗。**越接近最优，百分比越高、颗数越多**。

### 14.3 彗星分关榜 `pl{N}`（用户拍板：做分关榜）

- 每关一张小榜（与竞速 `rt{N}` 同构，动态 `scoreBoards` 已支持）：按该关 `P_lv` 降序，榜上展示"该关最优 token `levelBestToken`"供对照。
- 可选综合榜 `pl`：Σ 各关 `P_lv`（或平均），评估整体逼近度。**默认先做分关榜，综合榜后加**。

### 14.4 共存结构（不覆盖星星）

| 维度 | 存储键（建议） | 全局累计 | 胜利弹窗 | 进度条 |
|---|---|---|---|---|
| 星星（已有） | `function_chess_campaign_best_stars_{lv}` | `function_chess_campaign_stars` | 现有 5 星 | 现有星进度 |
| 彗星（新增） | `function_chess_campaign_best_comet_{lv}` | `function_chess_campaign_comet` | 新增彗星展示 | 新增彗星进度 |

- 胜利弹窗同时渲染星星与彗星（两套独立图标/进度），互不影响；重置进度时一并清空。

### 14.5 防作弊

- 彗星分由 `minToken` 推导，而 `minToken` 随 lr 的 `levels` 载荷一并上报 → 高分段复用方案二核验（token 复算，§4/§5）；`levelBestToken` 只从核验通过的记录更新。
- 进入"被举报强制核验"范围（D6：随 lr 一并核验即可）。
- 防"污染最优"：有人伪造极短 token 拉低 `levelBestToken`，因只取合法核验通过值 + 整批拒绝（D3），污染被堵死。
